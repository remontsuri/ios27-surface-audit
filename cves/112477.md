# CVE-2026-112477 — IOSurface notify race

| Field | Value |
|---|---|
| Component | `com.apple.iokit.IOSurface`, `s_set_surface_notify` (selector 17) |
| Class | use-after-free |
| Our status | **reproduced — DoS** |
| Build | iOS 27.0.1 (24A446), iPhone 14 (A15) |
| Full writeup | [`docs/01-iosurface-112477.md`](../docs/01-iosurface-112477.md) |

## What the CVE describes

A race between registering a notification callback and tearing down the surface client causes
the driver to use a freed listener node. The vendor wording is "unexpected system termination".

## What we measured

Triggering the race from a sandboxed app produced a kernel panic, reproduced across sessions.
The dispatcher walks a per-client list:

```
ldr x22,[x20,#0x188]     ; list head
loop:
  ldr x0,[x22,#0x58]     ; argument for the callback
  bl  <callback>
  ldr x22,[x22]
```

The panic register state from the device run:

```
pc 0xfffffff03786e014   lr 0xfffffff037287760
x0 = 0   x1 = 0xffffffdd36b84380   x2 = 0   x3 = 0xc4
FAR = 0x8   ESR = 0x96000006
```

`x0` is the value read from the freed node's `+0x58` field: zero, so the callback faults at
`[0 + 0xd8]`.

## Why it is not a primitive

The constructor writes the first 16 bytes of the user-supplied structure input into
`node+0x10` — and writes `self` (the `IOSurfaceClient`) into `node+0x58`. The dispatch path
reads `+0x58` only. A marker placed in the input buffer never appears in any register.

Typed-zone enumeration shows the freed slot can only be refilled by another notify node of the
same class, which writes a valid client pointer into `+0x58` again. So even a won race yields a
pointer to a different client, not an attacker-chosen value.

## Falsifier

Find any read, in the dispatch loop or the callback, of a field populated from the user buffer
(`node+0x10` and onward). Currently zero such reads exist.

## Public status

Fixed in 27.2 per public reporting. On 27.0.1 the branch is live but confined to DoS.
