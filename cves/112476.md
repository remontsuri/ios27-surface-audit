# CVE-2026-112476 — kernel out-of-bounds read (one number of a pair)

| Field | Value |
|---|---|
| Component | `kernel` per the advisory text; XNU `ipc_port` request table per one public lab |
| Class | out-of-bounds read / denial of service per the advisory; use-after-free per the same lab |
| Our status | **documented only** (corrected: not an info leak) |
| Build | iOS 27.0.1 (24A446), iPhone 14 (A15) |
| Pair | [`cves/112507`](112507.md) — same defect, second number |

## 1. What the public claim is

Two labellings exist, and the register keeps both rather than picking one:

| Source | Claim |
|---|---|
| advisory text as transcribed | "An app may be able to cause unexpected system termination" — denial of service, out-of-bounds read class, no PoC |
| a public verification lab (Cinder27) | `CVE-2026-112507 / 112476` — XNU `ipc_port.c` request-table consumers, use-after-free, "ipc_port request table index race" |

The lab's own source header carries both numbers on one file, so the two identifiers describe a
single defect. The register keeps two rows only because two numbers are cited publicly.

## 2. What was actually measured

**Not measured as such.** No run targets this number directly. The one device measurement in this
area belongs to the pair and is reported in [`cves/112507`](112507.md), condensed:

```
variant 64..71 -> -300 ((ipc/mig) client type check failure)
totals alloc=28800 notify=0 dealloc=28800
=== survived ===
```

That is a null result from a path that was never armed, not a test of the defect. With
`notify=0` the request-table consumers never run, so the interleaving the lab describes cannot
be constructed and the bug is never exercised. A run that cannot reach the site says nothing
about the site.

## 3. Why the status is what it is

`documented only`, with the correction kept. An early internal note filed this number as the
KASLR/infoleak partner for the IOSurface chain; that was wrong, and the error stays in the record
because a silently deleted misclassification comes back. The leak partner turned out to be
[`cves/112665`](112665.md).

Three statuses were available and two are wrong:

| Candidate status | Why not |
|---|---|
| `reproduced — DoS` | no panic from this path was ever produced here |
| `measured — denied` | denial needs a run that reached the path and did nothing; none did |
| `documented only` | matches the record: public description, no measurement |

## 4. The single falsifier

A panic whose faulting object is a freed `ipc_port` request-table entry — the fault follows
teardown of that entry, reached from a sandboxed app.

That would move the row to `reproduced — DoS` and no further. A primitive additionally needs the
reclaim step that [`cves/112477`](112477.md) fails on: the freed slot must be refillable with a
field the caller controls.
