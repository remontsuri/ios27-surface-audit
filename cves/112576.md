## 1. What the public claim is

Nothing was located. The number appears in this audit's own triage candidate list, and in no
advisory text, PoC, patch note or vendor string that could be checked here.

The register previously carried a class word for this row ("TOCTOU") with no source behind it.
That word is withdrawn rather than repeated: an unsourced class is a guess wearing the clothes of
a finding, and the class is exactly what a reachability check would need to aim at.

## 2. What was actually measured

**Not measured**, in either direction.

There is no measurement because there is no experiment to run. The reachability step this
repository uses everywhere else ([`CVES.md`](../CVES.md), "How a CVE enters this register", step 2)
starts by opening the component by name — nine provider names for [`cves/28992`](28992.md), one
IOKit connection plus a selector for [`cves/112477`](112477.md). Without a component name there is
no name to open.

| Required input | Held here |
|---|---|
| component / subsystem | absent |
| selector, call or file format | absent |
| class of defect | absent (withdrawn, see above) |
| public PoC or trigger | absent |

## 3. Why the status is what it is

`documented only` — and the word "documented" is doing real work: the number is recorded as seen,
nothing more. It is not `measured — unreachable`, because unreachability is a measured property
and nothing was measured. It is not `not tested` in the "out of scope" sense either: it was in
scope, it was simply never defined well enough to probe.

Recording it this way has one purpose: a reader can tell that the gap is *missing public detail*,
not a branch that was tried and abandoned. A register that quietly omits such numbers reads as
complete when it is not.

## 4. The single falsifier

A published description that names the subsystem **and** one sandboxed call or file open that
reaches it. That pairing is what moves the row from "unmeasured" to "measurable", and it makes the
next step mechanical:

1. match the service or open the file from a sandboxed app, recording the return code
   (the pattern in [`cves/28992`](28992.md) and [`cves/112477`](112477.md));
2. if the entry opens, run the described trigger and read the panic registers;
3. only then assign a status better than `documented only`.

No amount of reading the kernel cache substitutes for step 1: a fix site cannot be found by
searching for a number.
