# CVE-2026-112507 — `ipc_port` request-table index race

| Field | Value |
|---|---|
| Component | XNU, `ipc_port.c` request-table consumers (as described publicly) |
| Class | use-after-free from a stale index into a per-space request table (as described publicly) |
| Our status | **documented only** (the trigger was never armed; the arming precondition was measured) |
| Build | iOS 27.0.1 (24A446); the runs that exist were taken on the previous build, 24A437 |
| Pair | [`cves/112476`](112476.md) — same defect, second number |

## 1. What the public claim is

A public verification lab's index and its PoC carry this number together with CVE-2026-112476:
XNU `ipc_port.c` request-table consumers, use-after-free, described as an "ipc_port request table
index race".

The PoC's own source header states the shape and the fix:

```
The 27.2 kernel added ipr != NULL / table != NULL checks over every index-consumer
of the per-space port-request table.
```

Its trigger allocates RECEIVE rights, arms two notification kinds per port, then tears half the
ring down while the other half still holds armed notifications — four threads, depth 48, budget
6000.

Everything in that description depends on one step succeeding: **arming a notification on ports
the calling task owns.**

## 2. What was actually measured

A probe built from the lab's C twin ran three times on 24A437 (the build before the audit build;
never re-run on 24A446 after the OS update). It did not reproduce the race, because it never got
past the precondition:

```
=== kern.ipc CVE-2026-112507 start ===
task=515
variant 64 -> -300 ((ipc/mig) client type check failure)
variant 65 -> -300 ((ipc/mig) client type check failure)
...
variant 71 -> -300 ((ipc/mig) client type check failure)
chosen send=-1 dead=-1
race running
totals alloc=28800 notify=0 dealloc=28800
=== survived ===
```

Read the two numbers that matter:

| Counter | Value | Meaning |
|---|---|---|
| `notify` | `0` | not one notification was armed, so the request-table consumers never ran |
| `alloc` / `dealloc` | `28800` / `28800` | the port allocator itself was exercised and balanced; the run was not a no-op |

All eight variants (`64..71`) returned `-300`, the MIG client-type check failure. The loop then
ran to completion with nothing to race on, which is why the run ends `survived` rather than with a
panic.

## 3. Why the status is what it is

`documented only`, and deliberately not something better:

| Candidate status | Why not |
|---|---|
| `reproduced — DoS` | the race was never created; `notify=0` means the site was never entered |
| `measured — unreachable` | the refusal was measured on the previous build, not on 24A446; and a refused arming is a property of this call in this namespace, not proof the defect is out of reach on the audit build |
| `documented only` | matches the record: public description, plus a measurement of the precondition only |

The reason the audit did not pursue it further is structural, not tactical. The trigger needs a
notification armed against the calling task's port namespace; that call returns an error before
any request-table index is consumed. Thread count, ring depth and timing cannot repair a call that
fails on its first line, and a probe that keeps running after `notify=0` measures the allocator,
not the bug.

This is consistent with our reading of the lab's own journal, which files its ipc module as
`survived` rather than as one of the nine crashes; the journal totals are in
[`docs/07`](../docs/07-platform-limits.md) section 2.

## 4. The single falsifier

One `mach_port_request_notification` call returning `KERN_SUCCESS` (`0`) on a port the app owns,
followed by a fault whose faulting object is a freed request-table entry.

Both halves are needed, and they are worth different amounts:

| Step | What it would buy | What it would not |
|---|---|---|
| arming succeeds | the precondition is reachable; the ring teardown can be re-run | still no reproduction — a reachable trigger is not a fired one |
| a fault at a freed request entry | `reproduced — DoS` | still no primitive: the reclaim question would only then be worth asking |

That reclaim question is the one that ends every chain in this audit
([`cves/112477`](112477.md), closed on exactly that point).
