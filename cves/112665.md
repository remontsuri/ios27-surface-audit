# CVE-2026-112665 — kernel memory layout disclosure

| Field | Value |
|---|---|
| Component | kernel (address layout / KASLR information) |
| Class | information disclosure |
| Our status | **documented only** (never tested) |
| Build | iOS 27.0.1 (24A446), iPhone 14 (A15) |
| Related | [`cves/113910`](113910.md) — the other leak candidate, measured and denied |

## 1. What the public claim is

Advisory text, as transcribed during the audit: "An app may be able to determine kernel memory
layout" — information disclosure, remedy described as improved state management. Public
reporting places the fix in 27.2, which makes it live on the audit build. No function, no
trigger and no proof of concept accompany it.

The claim is the capability this audit was missing: one address, so that a use-after-free
([`cves/112477`](112477.md)) could be turned into something more than a panic. That is the only
reason it is in the register.

## 2. What was actually measured

**Not measured for this number.** No probe is bound to it: the one candidate the audit chased
under this heading, `rtm_scrub`, is documented without a CVE number and its reachability check is
negative. No run has returned a kernel address attributed to 112665.

Two results sit next to it, and neither is a test of it:

| Adjacent result | Measured value | Why it does not count |
|---|---|---|
| `rtm_scrub` / `dlil_ifaddr_bytes` candidate fix site | one call site differs between the audit build and 27.2; device probe: `interfaces=31 max_alen=6 over_8=0` | the site is not bound to this CVE number, and its precondition fails on this device anyway |
| decmpfs / Compression leak | tail zero-filled, no kernel pointers in the readable output | that is [`cves/113910`](113910.md), a different number |

The interface numbers are in [`evidence/04-interface-lengths.log`](../evidence/04-interface-lengths.log),
are explained in [`docs/04`](../docs/04-rtm-scrub-infoleak.md), and are re-checked by gate `G-RTM`.
That document does not name a CVE either — it records a candidate fix site, nothing more.

## 3. Why the status is what it is

`documented only` is the vocabulary entry for "read from public material, not measured here"
([`CVES.md`](../CVES.md)). It is deliberately not "blocked": a blocked branch has a measured
obstacle on the described path, and the one obstacle this audit did measure belongs to a site that
is not established as this CVE. A candidate that failed for its own mechanism cannot deny a
claim that was never tested.

It is also not `measured — denied`. Denial needs a run that reached the described path and
produced nothing; nothing of the sort happened for this number.

## 4. The single falsifier

One sandboxed call that returns a kernel address — a 64-bit value in the kernel text or heap
range — in a buffer the app can read.

The experiment that would produce it, in order:

1. locate the fix in the 27.2 kernel diff by normalised function signature (addresses move
   between builds, code does not);
2. identify the output buffer that carries the leaked value and the length that exposes it;
3. build the minimal caller and compare the returned bytes against a known kernel base.

Step 3 is the point where this row would change. Until it runs, the row stays where it is.
