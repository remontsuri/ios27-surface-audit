# CVE-2026-28992 — IOHIDFamily FastPath user client

| Field | Value |
|---|---|
| Component | `IOHIDFamily`, `IOHIDEventServiceFastPathUserClient` |
| Class | privileged user client reachable from apps (claimed) |
| Our status | **measured — unreachable** from a sandboxed app |
| Build | iOS 27.0.1 (24A446), iPhone 14 (A15) |

## Why it looked promising

A HID event user client is the kind of surface an app is allowed to touch (input events), and the
class does exist in the audited kernel. If a FastPath client were openable, it would be an entry
point to a kext that the sandbox usually hides.

## What was measured

A probe asked IOKit to open the service by every provider name associated with the family — nine
names including `IOHIDEventService`, `IOHIDEventDriver` and the FastPath class itself.

Result for all nine:

```
rc = 3758097089 = 0xE00002C1 = kIOReturnNotPrivileged
n  = 0
```

Meanwhile static checks confirm the class and both entitlement keys are present in the kernel
(`IOHIDEventServiceFastPathUserClient` appears 11 times; the entitlement helpers twice). So the
capability exists; the sandbox simply refuses the match.

## Verdict

The kext is reachable only for clients the sandbox trusts with HID access. From an ordinary app the
entry point does not exist — not "we could not exploit it", but "we cannot open it".

## Falsifier

Open any of the nine provider names from a sandboxed app without a special entitlement
(`kIOReturnSuccess` and a non-null connection).

## Note

This is the cleanest example in the project of the difference between *attack surface* and
*reachable attack surface*. The class being present in the kernel is necessary but not sufficient.
