| Field | Value |
|---|---|
| Component | CoreMedia bytestream service (media playback stack) |
| Class | sandbox escape — read-only file access |
| Our status | **reproduced — partial** (read yes, write no) |
| Build | iOS 27.0.1 (24A446), iPhone 14 (A15) |
| Full writeup | [`docs/02-bytestream-112706.md`](../docs/02-bytestream-112706.md) |
| Evidence | [`evidence/02-bytestream-read.log`](../evidence/02-bytestream-read.log), [`evidence/02-bytestream-write.log`](../evidence/02-bytestream-write.log) |

## What the CVE describes

A media client can ask the bytestream service for a file descriptor for a client-supplied
`file://` URL. The service opens the path with its own (system) privileges and hands the
descriptor back, bypassing the calling app's sandbox.

## What we measured — read

```
MediaLibrary.sqlitedb: VENDED fd=3 size=24592 direct_open_errno=1
PlayCounts.plist:      VENDED fd=3 size=8     direct_open_errno=1
iTunes_dir:            VENDED fd=3 size=0     dir=1 direct_open_errno=1
TRAV keychain:  refused code=-12203
TRAV TCC:       refused code=-12203
TRAV sms:       refused code=-12203
TRAV Library:   refused code=-12203
METRIC|...|vended=5 denied=10 bytes_read=24656 est=1|ESCAPE
```

Three of the vended descriptors are genuine crossings: the app's own `open()` on the same path
fails. The rest of the requested set is refused, so the capability is a **whitelist**, not
arbitrary file read.

The service also answers the existence question: `-12203` means "exists but forbidden",
`-17913` means "does not exist". That is a third capability (oracle) beyond reading and
directory listing.

## What we measured — write

Three rounds; the third fixed a control bug (the probe's own `open()` created the target, which
produced a misleading `EEXIST`).

```
W|own_wronly|own|opts=0xa01|REFUSED code=-12878
W|media_root|media|opts=0xa01|REFUSED code=-12878
W|mlib_rdonly|media|opts=0x0|fd=3|fl=0x0|size=24592
```

The service refuses writes on every external path, and also refuses to create a file in the
caller's own `Documents`. It cannot even see the app container (`-12203`).

## Entitlement independence

The same binary re-signed with only `get-task-allow` produced identical results, so the
behaviour belongs to the service, not to the client's entitlements.

## Why it is still not a jailbreak step

Read-only, whitelisted, no write, no code execution in a privileged process. It is stage one of
a chain and needs a second stage inside the media daemons.

## Falsifier

Vendor a descriptor for a keychain / TCC / messages database, or produce any successful write
through the service. Both are re-checked by `tools/gate.py` (`G-112706-READ`, `G-112706-WRITE`).
