# CVE-2026-113910 — kernel Compression / decmpfs memory disclosure

| Field | Value |
|---|---|
| Component | kernel compression (decmpfs) path |
| Class | kernel memory disclosure |
| Our status | **measured — denied** (no leak observed) |
| Build | iOS 27.0.1 (24A446), iPhone 14 (A15) |

## Why it mattered

This was the most attractive partner for the IOSurface use-after-free: an info leak would have
solved the first blocker of that chain (learning a kernel address). A "disclose kernel memory"
description with a live build is exactly what a stalled chain needs.

## What was measured

The decmpfs read path was exercised with a compressed file marked as uncompressed
(`chflags(UF_COMPRESSED)`), the configuration where an uninitialised tail would be returned to
the reader.

Result: the tail of the returned buffer is zero-filled. No pointer-looking values, no kernel
addresses, no residual heap content appeared in the readable output.

The kext diff against 27.2 shows two changed functions in `com.apple.kec.Compression` — consistent
with a hardening change, and consistent with the measurement: whatever the original defect was, it
does not produce readable kernel memory on this build.

## Verdict

Denied on device. The branch does not supply the leak that the IOSurface chain needs.

## Falsifier

Produce a read that returns non-zero bytes derived from kernel memory (address-shaped values whose
high half matches the kernel base range). A single such read reopens the branch.

## Consequence for the roadmap

With this denied and the KASLR-disclosure CVE untestable (no public trigger), the project has no
known info-leak primitive. That is stated plainly in the README rather than hidden.
